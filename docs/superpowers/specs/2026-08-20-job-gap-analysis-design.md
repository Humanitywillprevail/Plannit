# Job-role gap analysis (MVP)

Date: 2026-08-20
Status: approved, ready for implementation plan

## Context

This is priority #1 from a product review of Plannit's current state (see
project memory `project-plannit-overview`): the app has record-keeping,
LLM-based competency scoring (`lib/analysis/analyzeCourse.ts`, one score
1-5 per competency per course, stored in `CourseCompetency`), a lifetime
strength report (`/report`), and AI-generated portfolio narratives with PDF
export (`/portfolio`) — but nothing yet gives a user a reason to come back
every semester. Job-role gap analysis ("입력한 목표 직무 대비 부족한 역량
카테고리 피드백") is the feature meant to close that loop: it's the "record
→ analyze → concrete action" step that could substantiate Plannit's actual
differentiation claim (dynamic, cumulative data vs. one-time aptitude
tests).

Scope for this round is explicitly the MVP form only:
- Category-level feedback ("이런 유형의 경험이 부족해요"), never specific
  job postings, companies, or links — avoids LLM hallucination of listings
  that don't exist. Linking out to real postings (Linkareer/캠퍼스픽 등) is
  a later step, not this one.
- No new job-role → competency database. No crawling, no external data
  source.
- Results are not persisted — generated fresh per request, shown on the
  page, gone on refresh.

## Decisions from brainstorming

- **Framework source**: no static/hardcoded job→competency table. An LLM
  call judges, for a free-text job role, how important each of the
  existing 12 fixed competency categories (`COMPETENCY_DICTIONARY` in
  `lib/analysis/keywordDictionary.ts`) is — reusing the exact vocabulary
  `analyzeCourse.ts` already scores users against. This avoids building
  and maintaining a mapping table that can never fully cover free-text
  role names, and keeps the LLM's job to general category-importance
  judgment (low hallucination risk) rather than fabricating anything
  concrete.
- **Comparison is not an LLM call.** "Current profile" (already computed,
  reused as-is) vs. "required profile" (the one new LLM call above) are
  compared with plain arithmetic. The feedback sentences are generated by
  a template function, the same style as `lib/analysis/report.ts`'s
  `buildCompetencyReport` — not natural-language generation, so nothing in
  the output can state a fact the code didn't compute.
- **No persistence.** Chose ephemeral-per-request over a `JobGapAnalysis`
  DB model: simpler (no new schema/migration), and re-querying the same
  role always re-runs the LLM call anyway (no caching in this round) since
  free-text role spelling varies too much for an exact-match cache to be
  worth the complexity here.
- **Cold-start guard**: if the user has competency data for fewer than 2
  distinct courses, the page doesn't offer the analysis at all — it shows
  a message asking them to add more courses first, with a link to
  `/semesters`. Chosen over "run it anyway with a warning" because a gap
  report built from near-zero data would read as confident, specific
  feedback ("you're missing X") while actually being close to noise —
  worse than not showing it.
- **Cost**: the required-profile LLM call only fires when the user submits
  the job-role form (never on page load, never automatically) — same
  principle already applied to portfolio narrative generation
  (`generatePendingNarratives` in `lib/actions/portfolio.ts`).

## Data model

**No new Prisma models or migrations.** This feature reads `CourseCompetency`
(already exists) and calls an LLM; nothing new is written to the database.

## The scale-mismatch problem (the one non-obvious design point)

`CourseCompetency.score` is 1-5 **per course** (how strongly that
competency showed up in that one course, per `analyzeCourse.ts`). A user's
aggregate "current" strength in a competency is not naturally on a 1-5
scale — `lib/analysis/report.ts`'s `buildCompetencyReport` sums scores
across every course that touched that competency, so a competency that
shows up strongly across 8 courses will have a much larger raw total than
one that shows up once. The required-profile LLM call, on the other hand,
outputs a plain 1-5 "how important is this to the role" score. Comparing a
raw multi-course sum against a 1-5 importance score directly is meaningless
(a prolific note-taker would appear to have "more" of every competency
than the role could ever require).

**Resolution**: normalize the user's current strength in a competency to
the same 1-5 scale by averaging, not summing — `totalScore / distinctCourseCount`
for that competency (the average strength *when it does show up*), and 0
if the competency has zero `CourseCompetency` rows for that user at all.
This keeps both sides of the comparison on the same 1-5 meaning ("how
strong is this, on the scale the LLM already scores single instances on")
without inventing a new scale. It intentionally does not reward breadth
(showing up in many courses) over depth (scoring high when it does show
up) — breadth is a legitimate thing to weigh in a real gap analysis, but
adding it is more design surface than this MVP round needs; note it as a
candidate refinement if the "이런 게 부족해요" feedback ever needs to
account for "you only have this once, not zero, but it's thin."

## Components

### `lib/analysis/analyzeCourse.ts` (small modification)

Export `COMPETENCY_KEYS` (currently a local, unexported `const`) so the
new job-role module can reuse the exact same enum instead of re-deriving
it — one line change (`const` → `export const`), no behavior change.

### `lib/analysis/analyzeJobRole.ts` (new)

Mirrors `analyzeCourse.ts`'s shape:

```ts
export type JobRoleCompetencyRequirement = {
  competencyKey: string; // one of COMPETENCY_KEYS
  importance: number; // 1-5
};

export async function analyzeJobRoleRequirements(
  jobRole: string
): Promise<JobRoleCompetencyRequirement[]>
```

- Model: `anthropic("claude-haiku-4-5-20251001")` — same as
  `analyzeCourse.ts`. This is a structured classification task (rate 12
  fixed categories), not long-form prose, so Haiku is the right tier (contrast
  with the portfolio narrative generator, which uses Sonnet because it
  writes prose a human reads).
- Output schema (zod): `z.object({ requirements: z.array(z.object({ competencyKey: z.enum(COMPETENCY_KEYS), importance: z.number().int().min(1).max(5) })) })`.
  Deliberately no free-text field in the schema (no "reason", no
  "recommended companies", nothing) — the model has no field to put
  invented specifics into, even if it wanted to.
  Prompt: give the model the job role text and the 12 competency
  name/category list (same list format `analyzeCourse.ts`'s `buildPrompt`
  already builds from `COMPETENCY_DICTIONARY`), and ask it to rate general
  importance per category for that role, based on general knowledge of
  what the role typically involves — not tied to any specific company or
  posting.
- Throws on failure; caller catches (same convention as
  `generateNarrative`/`analyzeCourseCompetencies`).

### `lib/analysis/gapReport.ts` (new)

Pure, non-LLM — the template/arithmetic counterpart to
`analyzeJobRole.ts`, in the same relationship `report.ts` has to
`analyzeCourse.ts`.

```ts
export type GapItem = {
  key: string;
  name: string; // Korean competency name
  category: string;
  importance: number; // 1-5, from the role requirement
  currentStrength: number; // 0-5, normalized as described above
  message: string; // template-generated Korean sentence
};

export type GapReport = {
  jobRole: string;
  items: GapItem[]; // top 3-5 gaps, sorted by gap size descending
  summaryParagraph: string; // template-generated, "이런 유형의 경험이 부족해요" style
};

export function buildGapReport(
  currentRows: { score: number; competency: { key: string; name: string; category: string | null }; course: { id: number } }[],
  requirements: JobRoleCompetencyRequirement[],
  jobRole: string
): GapReport
```

- Compute `currentStrength[key] = totalScore[key] / distinctCourseIds[key].size` (0 if no rows for that key), from `currentRows` — same input shape `report.ts` already consumes (`prisma.courseCompetency.findMany` results), so the page can reuse one query for both `/report`-style display data and this.
- For each requirement, `gap = importance - currentStrength[key]`. Keep only `gap > 0 && importance >= 3` (don't flag "you're weak in X" when the role barely needs X anyway).
- Sort by `gap` descending, take top 5.
- If nothing clears the filter (the user's profile already covers what the role needs), `items` is empty and `summaryParagraph` says something like "지금까지의 기록만으로도 이 직무가 요구하는 역량을 고르게 갖추고 있어요" — a real, code-computed conclusion, not a placeholder.
- Sentence style/tone: match `report.ts`'s existing Korean voice (`joinKoreanList` helper, similar phrasing patterns) — reuse `joinKoreanList` from `report.ts` if convenient, or duplicate the ~5-line helper if importing from a page-oriented-sounding module feels wrong; implementer's call, not a hard requirement either way.

### `lib/actions/gapAnalysis.ts` (new, `"use server"`)

```ts
export type GapAnalysisState =
  | { status: "idle" }
  | { status: "error"; message: string }
  | { status: "result"; report: GapReport };

export async function analyzeJobGap(
  prevState: GapAnalysisState,
  formData: FormData
): Promise<GapAnalysisState>
```

Signature matches React's `useActionState(action, initialState)` contract
(prevState first, FormData second, returns the new state) — this is what
lets a Server Action drive client-rendered, non-persisted results without
a database round trip.

- `requireUserId()`.
- Read `jobRole` from `formData`, trim; if empty, return `{ status: "error", message: "직무를 입력해주세요." }`.
- Query `prisma.courseCompetency.findMany({ where: { course: { userId } }, include: { competency: {...}, course: { select: { id: true } } } })` — same shape `/report/page.tsx` already queries.
- Call `analyzeJobRoleRequirements(jobRole)` in a try/catch; on failure return `{ status: "error", message: "분석 중 문제가 발생했어요. 잠시 후 다시 시도해주세요." }` (mirrors the fail-soft convention used elsewhere, but here there's no "skip and continue" partial-success case — it's a single call, so failure means the whole request failed).
- Call `buildGapReport(rows, requirements, jobRole)`, return `{ status: "result", report }`.
- No `revalidatePath` — nothing was written.

### `components/GapAnalysisForm.tsx` (new, `"use client"`)

```tsx
"use client";
import { useActionState } from "react";
import { analyzeJobGap, type GapAnalysisState } from "@/lib/actions/gapAnalysis";
```

- `const [state, formAction, pending] = useActionState<GapAnalysisState, FormData>(analyzeJobGap, { status: "idle" })`.
- A text input (`name="jobRole"`) + submit button, `disabled={pending}` while running (same double-submit-guard convention as `GeneratePortfolioForm.tsx` from the portfolio feature, though here via `useActionState`'s own pending flag instead of a separate `useTransition`).
- Below the form: render based on `state.status` — `"error"` shows the message in a small error-styled line; `"result"` shows `state.report.summaryParagraph` plus a card per `GapItem` (competency name + category badge + `message`), matching the visual style of `/report`'s existing cards (`Card`, `Badge` components).

### `app/gap-analysis/page.tsx` (new)

- `requireUserId()`, `export const instant = false` (logged-in-only data, same convention as every other data page in this app).
- Count distinct courses with at least one `CourseCompetency` row for this user: `prisma.courseCompetency.findMany({ where: { course: { userId } }, select: { courseId: true }, distinct: ["courseId"] })`.
- If that count is `< 2`: render an `EmptyState` — "아직 분석할 기록이 부족해요. 과목을 2개 이상 등록하면 갭분석을 이용할 수 있어요." with a `Link` to `/semesters` ("과목 추가하러 가기").
- Otherwise render `<GapAnalysisForm />` inside the normal `PageHeader`/`main` shell used by every other page in this app (`/report`, `/portfolio`).
- This eligibility check lives only in the page (not duplicated inside the Server Action) — a deliberate scope decision: bypassing the UI to submit the form anyway would just produce a low-signal gap report against sparse data, not a security or data-integrity issue, so defense-in-depth here isn't worth the duplication for this MVP round.

## Error handling

- Empty job-role input: caught client-side by the `required` attribute on
  the input, and again server-side in the action (never trust client
  validation alone) — returns an `"error"` state, not a thrown exception.
- LLM call failure: caught in the action, returns an `"error"` state with
  a generic retry message — no partial-success case exists here (unlike
  `generatePendingNarratives`, which processes many records and skips
  failures individually; this action does exactly one LLM call per
  submission).
- Cold-start gate: handled entirely by the page not rendering the form —
  no error path needed once past that gate ensures at least 2 courses'
  worth of `CourseCompetency` data exists, though a report can still be
  fairly thin with exactly 2.

## Testing

Same convention as the portfolio feature: no automated test framework in
this repo. Verification is `tsc --noEmit` + `eslint` + `next build` (the
portfolio feature's final review caught a build-breaking bug that
`tsc`/`eslint` alone missed — `next build` must be part of verification
for any change touching `"use server"` files or new routes) + manual
exercise via a real browser session (fill in a job role, confirm the
result renders, confirm the cold-start gate shows correctly for a
low-data account).

## Out of scope for this round

- Any static job→competency database, curated role list, or dropdown of
  common roles — free-text only.
- Persisting analysis results (a `JobGapAnalysis` table, "analysis
  history," re-visiting a past result).
- Linking out to real job postings/companies (Linkareer, CampusPick, etc.)
  — explicitly deferred per the product roadmap (STEP2-3).
- Caching identical/similar job-role requests to save LLM calls.
- Weighting "breadth" (how many courses a competency appears in) alongside
  "depth" (average score) in the current-strength calculation.
- Any change to the portfolio AI-draft-prefill feature (priority #2) —
  that gets its own spec after this one is implemented.
